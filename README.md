# `@aiwa-codes/lander`

A reference build of the AIWA lander against
**AIWA Codes - Landing Page Motion Spec v1**.

It exists to be *looked at and lifted from*, not deployed. `apps/marquee` is
still the live site; this is the same content wearing the motion system from
the spec, so you can see each primitive working before deciding what to port.

```bash
pnpm --filter @aiwa-codes/lander dev     # → http://localhost:4300
```

No build step. `public/` is authored as final bytes and the server streams
them, so what you review is byte-for-byte what a visitor gets. The one
dependency-shaped thing here is `public/js/vendor/` - GSAP 3.15 and Lenis
1.3.26, vendored rather than loaded from a CDN because `apps/marquee`'s
`verify-no-cdn.mjs` gate exists for good reasons and this build should be able
to pass it unchanged.

---

## Content

Every word, screenshot and price comes from the shipping lander
(`apps/marquee/clone/index.html`), including the palette - the warm near-black,
the cream, and the `#fea002` amber that §2.3 needs to read as a 1px stroke.
Nothing here is invented brand. Where the spec asked for copy that did not
exist yet (panel 2's positioning line, the FAQ answers) it was written to fit
the existing voice.

  legal/{terms,privacy,acceptable-use,refund,cookies}.html   GENERATED, same.

Every builder returns a teardown (§5.2). `build()` in `main.js` collects them
and empties the list on every width resize; a leaked ScrollTrigger there is
what locks the page up after two or three breakpoint crossings.

## The rest of the site

The home page is one scroll-driven composition and is hand-authored. Everything
else is generated by `scripts/build-pages.mjs` into `public/`, committed, and
served with no build step - the same contract `apps/marquee` uses for its own
`overlay/legal/`.

```bash
pnpm --filter @aiwa-codes/lander pages:build    # write the pages
pnpm --filter @aiwa-codes/lander lint           # fail if they are stale
```

| URL | Source of its content |
| --- | --- |
| `/ai-website-builder` | Live copy, lifted from `apps/marquee/overlay/ai-website-builder.html` |
| `/ai-saas-builder` | Live copy, lifted the same way |
| `/ai-crm-builder` | Written here. The live page is a client-rendered shell with no prose in it |
| `/ai-app-builder` | Written here, same reason |
| `/docs` | Written here. The live site links straight out to `app.aiwa.codes/docs` |
| `/resources` | Written here, same reason |
| `/legal` and `/legal/<slug>` | `packages/shared/src/legal.ts` + `apps/web/src/content/legal.ts` |
| `/404` | Written here |

### Why a generator, in a package whose first line is "no build step"

Two reasons, and neither is that it was less typing.

**The legal copy must not be forked.** It is ~900 lines of versioned legal text
that already exists in one place, and `app.aiwa.codes` renders those same bytes.
Transcribing it here would fork the wording the day someone edits one side, and a
policy that says two different things on two hosts is the one kind of drift that
actually matters. `apps/marquee/scripts/build-legal.mjs` reached the same
conclusion first and this script is its descendant, markdown renderer included.

**The nav and the footer appear on fourteen pages.** A link inventory maintained
by hand in fourteen files is an inventory that is wrong in at least one of them.
`NAV` and `FOOTER_COLS` in `build-pages.mjs` are the only definition, and that is
why the script also writes into `public/index.html`: the home page is
hand-authored everywhere except its nav and footer, which are fenced by

```html
<!-- NAV:START (generated by scripts/build-pages.mjs - do not edit by hand) -->
```

sentinels and owned by the generator. Edit the inventory, run the script, and the
Docs link and the four builder pages land in all fourteen footers at once.

The output contract is unchanged, which is the part that matters: `public/` is
still final bytes, still committed, still served without a build step. Nothing
runs at request time and nothing runs at deploy time.

### What the footer carries

Lifted from what `apps/marquee` actually serves (its footer inventory lives in
`overlay/seo/nav-enhancements.js`): the four builder pages, Features, Workflow,
Made with, Pricing, FAQ, Docs, Resources, Templates, Connectors, Enterprise, the
five legal documents plus their index, the contact address and the four social
destinations. The legal column is DERIVED from `LEGAL_DOCS`, never typed, so a
document renamed upstream is renamed in the footer by the same edit.

One thing marquee has that is deliberately absent: **Join as a Partner**, which
points at `/early`. That page is an AIWA-built Vite SPA committed into
`apps/marquee/overlay/early/`, and it does not exist in this package. A footer
link to a 404 is worse than a missing one, so it is omitted rather than faked.

### Sub-pages reuse the primitives, they do not copy them

`page.js` imports `blurReveal`, `gradientText`, `marquees`, `blobs`,
`springHovers`, `accordion`, `footerReveal`, `navState` and `navMenu` from the
same `motion/` modules `main.js` uses, and adds one thing of its own: the `.toc`
current-section observer on a legal document. It does NOT load SplitText, the
hero, the pin, the horizontal track or `normalizeScroll` - a legal document has
nothing to pin, and a pin with nothing to pin is cost with no picture attached.

The rebuild contract is `main.js`'s, for `main.js`'s reason: a width resize kills
and rebuilds, a height-only resize is the URL bar and is ignored.

### Two things the server had to learn

`/legal/terms` and `/docs` are the published URLs, matching marquee's, so
`server/index.mjs` now resolves `<path>.html` and `<path>/index.html` in that
order - and refuses to for a path that already has an extension, because a
missing `.js` must 404 rather than quietly answer with a page. It also serves
`404.html` with a 404 status, never a 200.

## The four places this diverges from the spec

Each one is argued at length in a comment at the site of the change. Summary:

**1 · The hero canvas is live DOM, not a scrubbed `<video>` (§2.4).**
The footage does not exist yet - §8 open question 2 is literally "who produces
the hero screen recording". So the sequence §2.4 describes (prompt typed →
plan appears → files stream → preview renders → deployed URL) is *rendered*,
as a deterministic function of scroll progress. It scrubs at 60fps because
scrubbing is just setting a timeline's progress; there is no playhead to
stall, so the blob preloader, the 60%-in-2s readiness gate, the `seeking`
guard and most of the §2.8 fallback ladder are not needed and cannot fail. The
text stays real text - crisp at any DPR, selectable, ~0 bytes instead of 4MB.
When the footage lands: put the `<video>` in `.hero-media__frame` and point
the scrub at `video.currentTime` instead of `sceneTl.progress()`. The pin, the
handoff and the arrival reveal are untouched by that swap, which is exactly
why §7 says to build them in isolation.

**2 · The pin is `position: fixed`, not ScrollTrigger's pin (§2.4).**
ScrollTrigger's pin hands the element back to its document position when it
ends - 400vh above the fold. The handoff has to have taken ownership on that
exact frame or the canvas visibly snaps away. A permanently-fixed element is
the same visual result with no handover frame to get wrong, and it makes §6's
"no pin jump when the URL bar collapses" free.

**3 · The handoff interpolates against the destination's live rect, not
`Flip.fit()`'s snapshot (§2.6).**
`Flip.fit` measures the destination once. Ours is scrolling throughout the
handoff - which is the whole reason it feels like the card *arriving*. Against
a snapshot the media lands short, and the error grows with scroll speed; §6
asks for "no 1px drift, no overshoot" and a snapshot cannot promise it.
Reading the rect per frame is exact by construction, and it keeps working
after the handoff ends, so the card scrolls away with its section. Width and
height are animated, never scale, so the DOM inside genuinely re-lays-out -
the property §2.6 actually cares about. (GSAP's Flip plugin is therefore not
loaded at all, rather than shipped unused.)

**4 · The horizontal track's travel is measured, not `-(100 × (n-1) / n)%`
(§3.2).**
That formula is correct only when every panel is one viewport wide, which is
the build it was read out of. Ours are a fixed 26rem, so -80% overshoots and
strands the last panel with ~800px of dead space beside it - which §6
explicitly fails. The distance is now `track.scrollWidth - pin.clientWidth`,
re-measured on every refresh.

Two additions the spec does not cover, both because their absence is a defect
rather than a choice: a mobile nav (below 900px the links live behind a
toggle) and a full no-JS composition.

## The prompt arc

`.arc` is the one section with no direct line in the spec. It is our reading of
moto-card's currency wall - two columns of type bowing away from a headline so
the claim in the middle is felt before it is read. There the content is foreign
currency amounts and the claim is "0 FX fees"; here the content is the
sentences people actually type into AIWA and the claim is "Describe it. Ship
it." Same instrument, our own argument.

moto-card runs theirs on WebGL. The bow is a scale and an x-offset per item,
both derived from distance to viewport centre, and CSS transforms do that at
60fps for free - so this is transforms plus a CSS gradient, at roughly 1% of
the code for roughly 95% of the read. Below 760px the columns have no room to
arc (at 390px they meet in the middle and run through the headline), so the
same list becomes a horizontal marquee instead, fed from the same array.

## Tiers

| Tier | Condition | Behaviour |
| --- | --- | --- |
| 1 | ≥480px, motion OK | Full: scrub, handoff, horizontal scroll |
| 2 | - | n/a; see divergence 1: there is nothing to download, so there is no slow-connection branch |
| 3 | <480px | `.static-hero`: no scrub, hero collapses to one screen, spacer removed, canvas scoped to the hero, workspace well gets its own still |
| 4 | `prefers-reduced-motion` | Same shape as tier 3, canvas holds its poster frame |
| - | no JS | Same shape again, plus the states the entrance timeline would have applied |

Tiers 3, 4 and no-JS share one CSS block, because they want the same page.

## Verified

Checked in headless Chrome over CDP at 1440×900 and 390×844:

- No console errors on a full-page scroll, at either width.
- Resize 1440 → 400 → 1440 rebuilds cleanly: 21 → 16 → 21 triggers, tier class
  toggles both ways, nothing left hidden, no leaked triggers.
- Both marquee rows run at exactly 30 px/s despite a 1193px vs 1792px group -
  duration is computed from measured width, never hardcoded.
- The handoff lands with the media's rect equal to the well's rect, to the
  pixel.
- Reduced motion and script-disabled both render a complete, readable page.

And for the generated pages, at 1440x900 and 390x844:

- Every route answers 200: the four builder pages, `/docs`, `/resources`,
  `/legal` and all five documents. Every root-relative `href` in every generated
  page resolves (20 distinct targets, no 404s). A missing asset still 404s.
- Every generated page parses with balanced tags.
- The blob behind a page hero has no hard edge at any hero height. This took
  three attempts and the reason is written above the rule in `page.css`: the fix
  is `overflow-x: clip` on the body, NOT `overflow: hidden` on the hero (which
  draws a visible rectangle around the blob's tail) and NOT `overflow-x: hidden`
  on the body (which makes the block axis a scroll container and breaks the
  sticky table of contents). Verified by scanning rendered pixels for
  single-pixel brightness steps, not by eye.
- The agent grids are five items in a three-column grid, so the lead card spans
  TWO columns rather than site.css's three: 2 + 3 fills exactly, 3 + 1 + 1 leaves
  a hole. The seven-item feature grids keep the three-wide lead card, where
  1 + 6 does fill.

Not verified here: 60fps during the home page's scrub on real hardware, iOS
momentum, and Lighthouse. Headless throttles rAF to ~5fps, which is also why the
screenshots above were taken with reduced motion forced - it is the only way to
photograph the finished state of a blur-reveal in this environment.
